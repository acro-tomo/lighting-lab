## 1. 実績から読めること

2026-08-14 時点。リール21本のうち、尺・再生・リーチが揃っている19本で集計した。
累計は 保存4・シェア0・コメント0・フォロー獲得0。

| 群 | 本数 | 平均再生 | 平均リーチ | 再生÷リーチ |
|---|---|---|---|---|
| 16.3〜20.3秒 | 13 | 102.8 | 94.6 | 1.09 |
| 9.2〜13.7秒 | 6 | 147.8 | 119.3 | 1.24 |
| 短尺群から最高値(224/165)を除く | 5 | 132.6 | 110.2 | 1.20 |

### 1.1 短尺の再生増は「視聴者が増えた」ではない

内訳を出すと積でほぼ完全に説明できる。

- 短尺: 119.3（リーチ）× 1.24（ループ）= 147.9 ≒ 実測 147.8
- 長尺: 94.6 × 1.09 = 103.1 ≒ 実測 102.8

再生÷リーチの差（1.24 vs 1.09）は、10秒の動画が17秒より早くループ先頭へ戻るぶんの
計上差で、視聴完了の証拠ではない。実際に増えているのは「届いた人が約25人多い」ほう。
**短尺群は n=6・うち1本が外れ値なので、「短くすれば伸びる」はこのデータからは弱い示唆**。
ただし短くするコストはゼロなので、9〜12秒に寄せる判断自体は妥当。

### 1.2 リーチは内容ではなく固定プールで決まっている

長尺13本のリーチを並べると 44, 48, 51, 103, 103, 104, 104, 104, 107, 111, 112, 113, 126。
**8本が103〜126に固まる。** 上振れは165が1本、下振れは44〜51が3本だけ。
21本かけて一度もこのプールの外へ出ていない。

### 1.3 シェア0・フォロー0は「たまたま」では説明できない

累計リーチ1946・再生2223に対して、

- 保存率 = 4/1946 = **0.21%**（95%区間でおよそ 0.06〜0.52%）。低いのは事実。
- シェア・フォローは 0/1946。**3の法則**で真の発生率の95%上限は 3/1946 ≒ **0.15%**。

プレイブック2節は「シェア（DM送信）がリーチ拡大の最重要シグナル」を前提に置いているが、
そのシグナルが21本一度も発火していない。リーチが約110で固定されていることと整合する。

### 1.4 この母数では創作の良し悪しを判定できない

リーチ110・保存率0.2%なら、1本あたりの期待保存は0.22件。案が3倍良くても期待値は0.66件で、
観測は「0か1」にしかならない。**変数あたり30本以上ないと判別できない。**
したがってこの4本を「保存が増えるはず」と書くことはできない。書けるのは
**「これまで一度も動かしていない変数を1本ずつ入れる」**まで。

### 1.5 先に確認すべきこと（データの並べ替えだけでできる）

- 224/165 の1本が何だったか。**唯一プールを抜けた回**なので、他と何が違ったかを特定する。
- 44/48/52 の3本が直近かどうか。直近3本なら配信の縮小＝疲労のサイン、初期3本なら立ち上がり。
- 直近リールの **プロフィールへのアクセス数** と **リンクのクリック数**（→ 5節）。

### A｜天井に穴が1つもない部屋（10.5秒）★最推し

**0〜2秒の画**
天井の高さ近く（y≒2.6m）にカメラを置き、**わずかに見下ろすピッチのまま**、
継ぎ目のない白い天井が画面の上半分を占める構図。低い位置のペンダントの光が下から天井を舐めていて、
明暗のグラデーションだけが上半分にある。**照明器具も文字もロックアップも映っていない。**
カメラがゆっくり下降を始め、天井の縁が入ってくる。

> **見上げない。** AUDIENCE-AND-FORMAT.md の構図規約（テロップ帯 y=1000〜1500、主役は上半分）に従い、
> ピッチを下げて天井を画面上半分へ持ち上げる。当初案は天井を見上げるクローズアップだったが、
> 規約違反かつテロップ帯と競合するので破棄した。

**秒割り**

| 時間 | 画 | テロップ |
|---|---|---|
| 0.0-2.0 | 天井のみ。下降開始 | なし |
| 2.0-3.5 | 下降continue | 天井に穴がありません |
| 3.5-5.5 | 低いペンダントとブラケットが順に画へ入る | 灯りは9つあります |
| 5.5-7.5 | 部屋全体の引き | どれも低い位置です |
| 7.5-9.5 | 座位目線で静止 | これで暗いと思う？ |
| 9.5-10.5 | アウトロ | URL＋免責 |

**2秒で落ちない根拠**
断言はできない。言えるのは除去した要素が特定できること。既存21本は0秒目に見出しと暗幕があり、
止め絵の広告として判別できる状態だった。この案は0秒目に判別材料を置かず、
**天井という被写体としてありえない対象**が画面を占める。判別を約2秒遅らせるのが唯一の主張で、
n≈110では検証できない。

**触る理由の発生点**
最後のテロップ。**答えを出さずに終わる唯一の案。**「暗い」と思った人と「これでいい」と思った人が割れ、
片方は自分の間取りで確かめないと決着しない。夫婦間のDM送信が起きうる唯一の構造でもある（H1への反撃）。
CTAは「自分の間取りを読み込んで」ではなく **「リンクを開くとこの部屋が出ます」** に限定する。

**実装可否**
4本中いちばん確実。`public/demo/rooms/dk-copenhagen-apartment.json` が既に
ダウンライト0灯・ペンダント5＋ブラケット4の9灯（2400〜2700K / 260〜640lm / 8.6m×6.4m×H3.25m）で存在し、
カメラも目線高さ y=1.5 に設定済み。`?demo=copenhagen` の直リンクも実装済みなので、
**動画で見た部屋がそのまま開く連続性**が今日作れる。

- 要追加: `capture-decision-reel.mjs` に**カメラ補間モード**（現状は lights のみ / `:209-216`）
- **要確認**: 天井を舐めるカットで天井面が破綻せず映るか。
  `src/components/scene3d/lightingFill.ts:23-31` の `rasterBounceIntensity` は光束と床面積のみの関数なので、
  天井の見え方は実際に撮って確認する。

### D｜床の色を変えただけ（10.5秒）

**0〜2秒の画**
夜のLDK。**照明も家具もカメラも一切動かないまま、床だけが明るいオークから濃い色へ沈んでいく。**
壁の下半分の明るさが一緒に落ちる。文字なし。

**秒割り**

| 時間 | 画 | テロップ |
|---|---|---|
| 0.0-2.0 | 床が沈む | なし |
| 2.0-3.5 | 静止 | 照明は同じです |
| 3.5-5.5 | 逆方向に戻る | 変えたのは床だけ |
| 5.5-7.5 | 壁を白→中間色 | 壁も同じだけ効きます |
| 7.5-9.5 | 静止 | 色でここまで違います |
| 9.5-10.5 | アウトロ | URL＋免責 |

**2秒で落ちない根拠**
冒頭で**何が変わったのか分からない**状態が作れる。器具は同じなのに部屋が暗くなる。
この違和感の解消に約2秒かかる、というのが唯一の主張。

**触る理由の発生点**
2本目のテロップの瞬間。床材と壁紙は電気打ち合わせと同時期に決まる、読者が現在まさに持っている変数。
しかも他人の動画では自分の組み合わせを確認できない。
**既存21本はすべて「照明側の変数」で、部屋側の変数に触れた本が1本もない。**

**実装可否 — ここは断定できる。ラスター編集表示では効果がほとんど出ない。**
`src/components/scene3d/lightingFill.ts:23-31` の `rasterBounceIntensity` は
光束と床面積だけの関数で、マテリアルの色を参照していない。床を暗くしても間接的な明るさは変わらない設計。
反射の相互作用はパストレ側の効果。そのうえで現行の撮影スクリプト
（`capture-plates.mjs` / `capture-decision-reel.mjs`）は**すべてラスター表示のスクリーンショット**で、
パストレ表示を撮る経路が存在しない。

- **現実的な作り方**: ヘッダーの「レンダリング開始」で床色違い・壁色違いのPNGを手で3〜4枚書き出し、
  ffmpeg でクロスフェードする。追加実装ゼロ。透かしは `src/app/appUtils.ts:17-27` で右下に入る。
- **成立判定は既存の指標を使う。** AUDIENCE-AND-FORMAT.md の「成立しなかった軸」に、
  1080相当へ縮小してRGB差を取り **|Δ|>12 の画素の割合** で絵になるかを測った実績が残っている。
  目視ではなくこれで判定する。記録されている水準は次のとおり。

  | 実績 | 変化画素 | 判定 |
  |---|---|---|
  | 数灯だけ色温度を変える | 0.1〜2% | 絵にならない |
  | ロフトのアイランド＋キッチン5灯 | 22〜36% | 見た目は弱い |
  | 第3弾⑧ コペンハーゲンの低い灯り群 | 92% | 採用 |
  | 全灯 2700K→6500K（対照） | 99% | 明確 |

  **目安は40%以上。** 36%以下は「弱い」と実測済みなので不成立として捨てる。
  床は画面占有面積が大きいので数灯の色温度変更より有利なはずだが、
  ラスター表示ではバウンスが色を見ていない以上、最終レンダー同士で測らないと意味がない。
  **4本の中で唯一、着手前に検証が必要。**

## 4. 優劣と、落とした案

**A が最上位である理由は3点。**
(1) 既存アセットで今日撮れる。(2) 唯一「答えを出さずに終わる」＝H4への直接の反撃で、
シェアとコメントが発生しうる唯一の構造。(3) `?demo=copenhagen` で動画と着地画面が完全に一致する。
C は狙いが最も鋭いが新規実装が3つあり、B は効果が地味で既出のウォークスルーと見分けがつかないリスクがあり、
D は内容がいちばん強いのに成立するかどうかが検証待ち。

| 落とした案 | 理由 |
|---|---|
| 同じ照明計画を別の間取りに移す | `six-rooms.reel.json` の「間取りが違えば照明も変わる」と論点が同一 |
| 天井高 2.4m vs 2.6m | 新軸だが、読者は電気図面を持つ段階＝天井高は確定済み。行動に接続しない |
| 方位を90°回す | 夜が主戦場のこのアカウントでは差が出にくく、「大きな窓の昼と夜」と重なる |
| 夜の窓の映り込み | 同上と重複気味＋ガラス反射のレンダー表現が要確認で確度が低い |
| 階段・吹き抜けの足元 | 新軸だが「見落とし指摘型」で、不安喚起の連投になる。温存 |
| 配線は動かせないが器具は変えられる | 8/15予約分の直接の対になるが論点が近すぎる。8/15の反応を見てから |
| 「リンクを開くとこうなる」単体のCTAリール | 案Cに吸収。単体だと宣伝色でリーチが落ち、n≈110では検証もできない |

## 5. 動画より先に効く手当て

リーチ110の1本が生むリンク開封は、どんなに良くても数人。**4本作っても絶対数は変わらない。**
そして今の状態では変わったかどうかも分からない — リポジトリに解析コードは一切なく
（`functions/api/` はフィードバックのみ）、ツール利用の観測手段が存在しない。

**先に見るべき2つの数字**

- プロフィールアクセスが1本あたり0〜2 → 動画が profile visit を作れていない。案A・Cの設計がここに効く。
- プロフィールアクセスが10以上でクリック0 → 問題は**動画ではなくプロフィール文とリンク先**。4本作っても無駄。

**動画より期待値が高い3つ**

1. bioのリンクを `?demo=copenhagen` 等の直リンクにする。実装済みなので設定変更だけ。
2. スマホでキーボードショートカット10行を出さない（`IntroGuide.tsx:44-60`）。
3. CTAの宛先を「自分の間取り図の読込」から「サンプルの部屋」へ変える。
   壁の自動認識は未実装なので、自分の図面から始める経路はリール直後に踏める行動ではない。

## 6. 4本に共通して必要な制作変更

現行の `scripts/instagram/encode-reel.mjs:96-175` は全フレームに
scrim・ロックアップ・eyebrow・見出し・sub を固定で乗せる。4本とも成立させるには3つ変更が要る。

1. **冒頭を素の映像にする。** テキストなしショットを許す。
   現状は `TEXTS[shot.id]` が必須で（`:196-201`）、無条件に見出しが描画される。
2. **1画面1文モード。** 現状は eyebrow＋見出し3行＋sub＋cta の同時表示。
   eyebrow / sub を省略できるようにする（省略すると `undefined` が描画される）。
3. **AI音声は入れない。** AUDIENCE-AND-FORMAT.md の実測は 5.8字/秒で、
   ショット尺からxfade分の0.4秒を引いた範囲に収める規約。1.5秒ショットなら
   (1.5−0.4)×5.8 ≒ **6字**しか入らない。**尺を9〜12秒にした時点で音声は物理的に成立しない。**
   21本すべてにAI音声が入っていたので、無音であること自体も未検証の変数になる（効くとは主張しない）。

実際に作るときの手順とプロンプトは [PRODUCTION-PROMPT.md](PRODUCTION-PROMPT.md)。
